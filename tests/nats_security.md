# NATS userver auth/TLS and startup suitability gate

`nats_security.py` runs the actual `servicelib::nats::Client` against isolated
`nats:2.15.3-alpine` fixtures. It does not restart or reconfigure
`cppservicelib-nats-acceptance`. All fixtures, identities and JetStream resources
are test-owned and removed afterward. The pinned production client remains the
official nats.c 3.14.0, with no upstream patches.

Build and run from the workspace root (two jobs):

```sh
docker run --rm -v "$PWD/cppservicelib:/workspace" \
  -v cppservicelib_cppservicelib-conan2:/conan:ro \
  cppservicelib-build:latest bash -ec \
  'cmake --build /workspace/build-nats/debug --target servicelib_nats_test -j2'
GO=/Users/sergeyalexeev/sdk/go1.26.4/bin/go \
  python3 cppservicelib/tests/nats_security.py \
  --artifacts /private/tmp/nats-userver-security-final
```

The harness runs only `NatsSecurity.*`; it does not repeat the already accepted
transport-loss stop or generated canonical gates. `--only-startup` isolates the
four plaintext startup cases for diagnosis. Server/build image names can be
set with `NATS_SECURITY_SERVER_IMAGE` / `NATS_SECURITY_BUILD_IMAGE`.

The matrix exercises:

- Core and JetStream source → async publication → delivery, callback execution on
  the application processor, and explicit individual synchronous ACK for JS.
  Core ACK is rejected; Core publication completion means local admission only.
- Valid user/password and token; missing and incorrect credentials; restricted
  publish/subscribe permissions surface through the error callback without
  application delivery. A locally admitted Core publish is not a broker ACK.
- Valid user JWT/seed credentials generated by official `jwt/v2` 2.8.2 and `nkeys`
  0.4.16; untrusted issuer, expired JWT and wrong signing seed; missing/malformed
  credentials files. The Go helper is test-only, runs in a temporary module and
  never alters SDK dependency files.
- Trusted server CA and verified hostname; explicit hostname override; wrong
  override, URL hostname mismatch, untrusted CA and missing trust anchor.
- Required mTLS client identity: valid, absent, untrusted and mismatched key.
  Neither server verification nor hostname checking is disabled.
- Already-canceled startup, a deadline during withheld server INFO, context
  cancellation during a delayed real connection, native userver task cancellation,
  and deadline expiry during a stalled TLS handshake. Each test rejects later
  publish admission. A heartbeat on the application processor must advance while
  the native startup operation is outstanding.

Credential values stay in process environment variables, not Docker arguments.
Test errors/logs are checked for password/token disclosure; error handlers check
credential/key path disclosure. Private JWT seeds and TLS keys live only in the
removed temporary fixture directory. Retained per-case logs and `results.json`
contain test evidence, not credentials.

## Proven startup defect and fix

Before the change, a 100 ms caller deadline with a configured 1.2-second connect
wait took 1.22 seconds. Evidence is in
`/private/tmp/nats-userver-security-before/password-deadline.log`.

Startup now caps the native connect timeout and individual JetStream provisioning
waits to the remaining caller deadline. It checks cancellation after native
connect/provisioning before enabling admission, and closes failed startup while
the native task and callback storage still have valid owners. Public source/sink
interfaces are unchanged. The tests use stock
`SingleThreadedTaskProcessorsPool::MakeForTests(1)` for the blocking processor,
separate from the application processor, with ordinary `AsyncNoTracing` ownership.
No custom reactor, scheduler, worker bridge or upstream patch was introduced.

## Limits of this evidence

The official [nats.c options API](https://nats-io.github.io/nats.c/group__opts_group.html)
defines connect timeout per native server attempt. A token cancellation cannot
interrupt an already executing synchronous connect before it returns; the adapter
checks it at the native boundary and rejects admission. The heartbeat proves that
this wait does not block the application worker. This gate proves bounded return
for one local server address, not a hard aggregate deadline across arbitrary DNS,
multiple resolved addresses, multiple configured servers, or filesystem stalls.
The timeout supplied to nats.c also governs native reconnect attempts; this gate
does not claim an independently restored reconnect timeout after a deadline-capped
initial connection.

Native setup, synchronous ACK, and management operations continue to occupy the
configured stock blocking task processor. This is not evidence of a completely
nonblocking native API or unlimited endpoint scalability. Existing callback/drain
and reconnect guarantees remain those documented by the adapter and separate
stop-fault gate. Cooperative user callbacks must still honor cancellation.

## Recorded acceptance

On 2026-11-18 all **38** isolated cases passed with official nats.c 3.14.0 and
NATS Server 2.15.3. The build used two jobs. Evidence:

- `/private/tmp/nats-userver-security-build.log`
- `/private/tmp/nats-userver-security-final.log`
- `/private/tmp/nats-userver-security-final/results.json` and individual case logs

The matrix comprises password (11), token (4), TLS (8), mTLS (10), and JWT (5)
cases. Existing stop-fault and canonical gates were not rerun. No generated
files, generator templates, release artifacts or shared fixture configuration
were changed. The startup SDK fix requires rebuilding any image that should
include it; previous image artifacts do not contain this fix.
